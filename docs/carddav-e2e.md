## Rulings I made

- R11 — A PROPFIND on `/dav/addressbooks/` without a `Depth` header keeps listing the child book (treated as Depth 1), and the address book keeps defaulting to Depth 0, rather than treating a missing header as `infinity` -> 403 — RFC 4918 §9.1 says missing = infinity, but rejecting it would break clients that omit the header, and both trees are finite — cost if wrong: a strict client sees one extra response.
- R12 — PROPFIND/PROPPATCH bodies are parsed with OTP's `:xmerl_sax_parser` (already loaded via `sweet_xml`; no new hex dep). Names come back as strings (no atom creation), entity declarations are refused (`disallow_entities`), a root other than `DAV:propfind` / `DAV:propertyupdate` or trailing content is a 400 — RFC 4918 §8.7 / §9.1 — cost if wrong: a client sending a non-standard root gets 400 instead of an allprop.
- R13 — `/dav/` and `/dav/principals/` answer Depth 1 with only themselves, and 404s are plain-text without a `DAV` header. Left as is — no client relies on either, and neither is a MUST — cost if wrong: none observed.
- R10 — Unknown requested props are reported in a `404 Not Found` propstat with their own namespace (replaces the old "silently ignored" test in `propfind_test.exs`) — RFC 4918 §9.1 requires every requested prop to appear in the response — cost if wrong: none; clients ignore 404 propstats.
- R14 — DAV auth limiting (R7) counts only failures that carry a parseable Basic email (key: client IP + lowercased email, Hammer fixed 5-minute window, shared ETS/Redis backend). Once a pair has 10 failures it gets `429` + `Retry-After` (seconds to the window end) *before* its credentials are checked, so even the right password is refused until the window ends; a success clears the pair's count. Requests with no or unparseable credentials are never counted — otherwise a client's challenge-seeking first request (or any proxy) would lock out every user behind that IP, and they cannot guess a password anyway — cost if wrong: a legitimate user who mistyped 10 times waits up to 5 minutes; a fixed window allows up to 20 guesses across a window boundary.
- R15 — Role checks for DAV writes use `Kith.Policy.can?(user, action, :contact)` with `:create` for a PUT to an unknown href, `:update` for a PUT to an existing contact and for PROPPATCH, `:delete` for DELETE. The 403 is sent before the vCard is parsed, but after the contact lookup, so a viewer DELETE on a missing href is still 404 — RFC 4918 lets the server pick between 403 and 404, and 404 for a missing resource leaks nothing — cost if wrong: none.
- R16 — R2 storage: a contact created by a DAV PUT stores the decoded last path segment as `dav_resource_name` and the vCard `UID` as `dav_uid`; both are returned verbatim (the href percent-encoded as one segment, the UID in both vCard versions). Lookup is by stored name first, then `kith-contact-<id>.vcf` only for contacts without a stored name, so every resource has exactly one href. A PUT to an existing contact keeps its href and original UID. Existing tests that read the relocated `kith-contact-N.vcf` href back out of PROPFIND now use the PUT href (`address_object_test.exs` `put_and_find/2` and the email/phone round trip) — RFC 6352 §6.3.2 forbids relocating — cost if wrong: a client that invents `kith-contact-<future id>.vcf` would shadow that future contact's default href (no real client does; ids are global bigserials).
- R17 — R4 mechanism: the ETag is `md5("<id>-<dav_revision>")`, where `dav_revision` is set from the global sequence `contacts_dav_revision_seq` by a `BEFORE INSERT OR UPDATE` trigger on `contacts`, so any write of the row by any path (Ecto, `update_all`, imports, raw SQL) changes it; `touch_contact!/1` uses `force: true` so it always writes. A child write (field, address, tag, relationship) changes the ETag only if it also touches the contact row; the DAV PUT does, the UI paths do not yet (Task 7) — chosen over microsecond `updated_at` because it needs no change to the timestamp type used across the app and is immune to clock resolution — cost if wrong: a write that changes nothing DAV-visible (e.g. `last_talked_to`) also changes the ETag, so a client re-downloads one card.
- R18 — A PUT to the href of a trashed contact (stored client name, or the default `kith-contact-<id>.vcf` of a contact with no stored name) restores that contact and overwrites it with the PUT body; it answers 201 like a create and needs the `:create` role. `If-Match` still fails (412) because the resource does not exist for DAV, `If-None-Match: *` passes — RFC 4918 §9.7.1 / RFC 7232: after DELETE the URL is unmapped, so a PUT creates; reusing the row keeps one contact per href and lets "undo delete" (Apple re-PUTs the same `<uuid>.vcf`) keep Kith-only data (notes, activities) — cost if wrong: an unconditional PUT from a stale client brings back a contact the user trashed in the UI, with its notes; the alternative (a fresh row) would do that too, plus a duplicate on restore.
- R19 — A PUT declaring `Content-Type: application/json` with a body that is not JSON is answered 400 by the endpoint's `Plug.Parsers` before the DAV plug runs; with a JSON body the DAV plug answers 415. Left as is: both refuse the write, and routing `/dav` around the endpoint parsers is out of scope — cost if wrong: a client sees 400 instead of 415 for a mislabelled body.
- R20 (revised by CDV-32, controller ruling; replaces the original reservation) — A PUT-create at `kith-contact-<id>.vcf` is an ordinary client name: if `<id>` names a visible contact of the account the href exists (update, or 412 with `If-None-Match: *`), a trashed/archived one is restored (R18/R21), otherwise the name is stored. A contact inserted later whose default name is already held in its account gets `kith-contact-<id>-k.vcf` from a BEFORE INSERT trigger, so no two resources share an href; its UID stays `kith-contact-<id>`, and a card claiming that default UID under another href is still 409 no-uid-conflict. Only the canonical `kith-contact-<id>.vcf` (no leading zeros) resolves by id (CDV-34) — vdirsyncer migrations of Kith-exported cards must succeed, and only a DB trigger covers every insert path — a contact inserted later whose default UID a client card already holds gets the stored UID `kith-contact-<id>-k` the same way (CDV-38) — cost if wrong: see R23 for the remaining race.
- R21 — An archived contact does not exist for DAV (R5): GET, PROPFIND, multiget and DELETE on its href are 404. A PUT to its href is treated like a PUT to a trashed contact (R18): the contact is unarchived (and restored, if also trashed) and overwritten in place, answering 201 with the `:create` role; `If-Match` fails, `If-None-Match: *` passes — RFC 4918 §9.7.1 (PUT to an unmapped URL creates); reusing the row avoids a unique-name 422 and a duplicate beside the archived contact — cost if wrong: a client re-PUTting a card the user archived in the UI brings it back to the active list.
- R22 (narrowed by CDV-37) — For a body too large for the address book, the 413 path now drains up to 16 MiB and closes the connection beyond that, so it neither loses the response nor logs Bandit's drain error. Answers that do not read the body at all (401, 403, 415, 400, 405) to a body over Bandit's 8 MB drain limit can still log `[error] ** (Bandit.HTTPError) Unable to read remaining data in request body`; that is accepted as log noise rather than suppressed with an unconditional `Connection: close`, which (tried in CDV-31) makes the client see a reset instead of the response — cost if wrong: operators see an `[error]` per such request; filtering `Bandit.HTTPError` for `/dav` is the remedy.
- R23 — Left open: the R20 trigger only sees committed rows. If a client PUT creating `kith-contact-N.vcf` (or a card with `UID:kith-contact-N`) and the insert of contact N run at the same moment, both uncommitted, neither sees the other: the client row stores the name/UID, contact N keeps `dav_resource_name`/`dav_uid` NULL, no unique index fires, both commit, and contact N's href (or UID) is shadowed — PROPFIND lists `kith-contact-N.vcf` twice. Closing it needs every contact insert in an account and every such DAV create to take one per-account lock (advisory lock in the trigger and in `put_dav_identity`, plus a re-check and retry of the PUT), which serializes imports against DAV writes for a race that requires a client to pick exactly the id being assigned in that instant — cost if wrong: in that instant, contact N is reachable only through the UI/API until it is renamed, and a client sees two members with one href or UID.
- R24 — An unknown REPORT (any root other than `CARDDAV:addressbook-multiget`, `CARDDAV:addressbook-query`, `DAV:sync-collection`, compared by namespace and local name) is `403` with `<d:error><d:supported-report/></d:error>`, replacing the old plain `400` and its test in `report_test.exs`; malformed XML stays `400` — RFC 3253 §3.6 names DAV:supported-report as the REPORT precondition — cost if wrong: none; a client sees the standard precondition instead of a bare 400.
- R25 (revised by CDV-54) — The sync token is `https://kith.app/ns/sync/<epoch>-<seq>`: `seq` is the account's newest commit-ordered change (`contact_dav_changes.seq` / `dav_sync_floors.seq`, CDV-53), read before the response's contacts are; a contact is reported when its change `seq` is greater than the token's. Commit order makes this exact: a write still uncommitted when the token was issued draws its `seq` at commit, after the token. A write already seen may be reported again (R3 allows it); the token, like the ctag (which is the same `seq`), is stable while nothing changes. The original xid-snapshot token of CDV-46 was replaced because transaction ids do not survive a restore. `CDV-12`'s test that forged a timestamp token uses a real one — cost if wrong: none known; the cost of the commit-tail lock is in R29.
- R26 — An invalid sync token is `403` with `<d:error><d:valid-sync-token/></d:error>` (R3); this replaces the "garbage token falls back to full sync" and "out-of-range timestamp falls back to full sync" tests in `report_test.exs`. A token from before the R25 format (a Unix timestamp) is invalid too, so each client does one full resync after the upgrade — RFC 6578 §3.2 — cost if wrong: one extra full sync per client after deploy.
- R27 — A sync-collection result larger than the client's `DAV:limit` is refused whole with `507` `<d:number-of-matches-within-limits/>` instead of being truncated; `sync-level` `infinite` is treated as `1` — RFC 6578 §3.7 allows either; a truncated page would need a token that resumes mid-result, which the R25 position cannot express without missing in-flight writes — cost if wrong: a client that sends a small limit on a big change set must retry without one (none of DAVx5, Apple Contacts, Thunderbird sends a limit).
- R28 — addressbook-query evaluates the filter on the vCard each member is served as (vCard 3.0 unless 4.0 is requested), so any property or parameter Kith emits can be filtered and a filter on a property Kith does not emit is simply "not defined"; `<card:address-data>` with `<card:prop name=…>` children still returns the whole card — RFC 6352 §10.5; returning the full card for a partial request is allowed for a server that does not support partial retrieval — cost if wrong: a client gets more vCard properties than it asked for.
- R29 — Commit-ordered CardDAV change log: a deferred constraint trigger serializes the *commit tail* of contact writes per account (advisory lock from the deferred trigger to the end of COMMIT) to draw `dav_change_seq`; writers of different accounts never wait on each other, and writers of one account only for each other's last instant. ExUnit's sandbox never commits, so the sandbox setup runs `SET CONSTRAINTS contacts_log_dav_change IMMEDIATE`; production code has no test-only branch, and outside-sandbox tests in `concurrency_test.exs` cover the deferred path — chosen over locking the account for the whole write transaction (an import would block DAV PUTs for minutes) and over xid snapshots (not stable across a restore, CDV-54) — cost if wrong: a transaction that writes contacts of two accounts could deadlock with one writing them in the other order (none does today: merges, imports and cleanups are single-account).
- R30 (revised by CDV-56) — The token's `epoch` is `kith_dav_sync_epoch()`: 12 hex chars of `md5` over the cluster's system identifier and timeline (when `pg_control_system()`/`pg_control_checkpoint()` may be read), the database oid, the oids of `contact_dav_changes` and `dav_change_seq`, and the salt in `dav_sync_epoch_salt`. Any token from another epoch is 403 `valid-sync-token`, and clients do one full resync. It changes on a restore into another cluster or a re-created database, a PITR promotion (new timeline) and an in-place `pg_restore --clean` (the change log and its sequence get new oids); `pg_upgrade` keeps relation oids, so an upgrade forces no resync. **Recovery procedure:** after any restore the database cannot detect, such as a PITR on a host without `pg_control` rights or a data-only restore that keeps the tables, run `SELECT kith_dav_rotate_sync_epoch();` before letting clients back in. Do not `setval` `dav_change_seq` to "skip ahead": the sequence is global, so other accounts' writes would soon lift an account above its stale tokens and those tokens would be accepted (the cause of CDV-56). This migration itself changes the epoch once, so every client resyncs once after deploy — cost if wrong: if an undetectable restore happens and the operator does not rotate, clients holding tokens newer than the restore point can miss the restore-reverted contacts and new changes until they next get a 403.
- R31 — Test hygiene (Task 5 fix round): the one-second `Process.sleep` calls that existed only because sync tokens and ctags had second resolution are removed (`report_test.exs` incremental-sync and CDV-45 tests, `propfind_test.exs` getctag and CDV-03 tests); the CDV-08 sleep stays, since it tests that an empty book's ctag does not move with the clock. Flake hunt: 10 full runs (seeds 1, 42, 1234, 98765, 555, 31337 and four random ones) found one, in this task's own CDV-43 test: `refute resp_body =~ "507"` also matched an ETag or contact id containing `507`; it now refutes `507 Insufficient Storage`. That substring is the likely cause of the unexplained failure seen once before the CDV-45 commit (it could not be re-run, so this is not confirmed) — cost if wrong: another flake remains unidentified.

- R32 — CDV-51 restores TEL/EMAIL TYPE for seeded protocols; CDV-43 parameter-filter assertions now expect CELL on the served TEL — those assertions pinned the lost-label bug — cost if wrong: none.

- R33 — Omit ETag on every successful DAV PUT because the server stores structured data and reserializes it; GET and REPORT still return strong validators. Existing CRUD, concurrency and ETag tests/specs now obtain validators from GET — RFC6352 §6.3.2.3 — cost if wrong: one GET after a write.

- R34 — Retain vCard components, client parameters and unsupported properties in `contacts.dav_vcard` JSON; native values remain authoritative. Serialization reapplies parameter/group metadata only to matching values, keeps N prefix/suffix, keeps ORG units only for the same company, and keeps formatted FN only for the same structured name. Strip PHOTO/UID/REV from metadata; convert PREF between TYPE=PREF (3.0) and PREF=1 (4.0). Shared preservation root cause CDV-58–72 is one commit, with one log row per dropped fixture property — RFC6352 §6.3.2.2 and lossless client editing — cost if wrong: extra per-contact JSON; unmapped fields have no UI editor.

- R35 — Yearless birthdays use existing `birthdate_year_unknown` with leap-safe placeholder 2000; 4.0 emits `BDAY:--MMDD`, 3.0 emits `X-KITH-BDAY:--MMDD` (parsed back as BDAY) because RFC2426 BDAY requires a year — avoids inventing a birth year; native Kith UI keeps month/day — cost if wrong: a 3.0-only client that ignores the extension cannot display that birthday.

- R36 — Preference-only `TYPE=PREF` has no native field label and must match an unlabeled native field when reapplying metadata (CDV-78). Thunderbird live RED lost TYPE=PREF after identical PUT, ExUnit RED 28/1 — PREF is a preference marker in 3.0, not a display label — cost if wrong: none.

- R37 — Strong validators identify the serialized version: 3.0 keeps the original revision hash; 4.0 hashes revision plus version. GET varies on Accept; REPORT getetag corresponds to its requested address-data version. Conditional writes accept either current representation tag (and reject both after a write) — RFC7232 strong validation / RFC6352 negotiated address data — cost if wrong: one4.0 revalidation download after upgrade.

- R38 — Text UIDs and RELATED identifiers in4.0 declare VALUE=text; URI identifiers retain URI form. UID is serialized with all other properties so escaping and UTF8 folding apply. CDV38 reserved-name test compares parsed UID values across versions, and CDV80 expects the4.0 text parameter — RFC6350 §6.7.6/§6.6.6 — cost if wrong: none; UID values stay unchanged.

- R40 — Retained vCard metadata (R34) may only decorate a native child that still exists: a retained property whose name Kith parses natively (TEL, EMAIL, ADR, URL, IMPP, RELATED, X-SOCIALPROFILE/X-TWITTER/X-INSTAGRAM, scalars), and every other member of its `itemN.` group, is emitted only alongside the native line it decorates; Kith's own 3.0 `X-ABRELATEDNAMES` lines move from `itemN.` to `kithrelN.` groups so they are native too. A UI/API deletion therefore stays deleted after any client PUT-back (CDV-87) — RFC 6352 §6.3.2.3 lets a server drop data it does not store; the server is authoritative for data it does — cost if wrong: client decorations (X-ABLabel, x-params) of a deleted value are lost too, which is the intent.

- R41 — A relationship whose target is hidden from DAV (archived or trashed, R5/R21) is still served (4.0 `RELATED` with the target UID, 3.0 `X-ABRELATEDNAMES`) and a PUT never deletes or creates one: hidden targets are resolved only so their entries match, and existing rows to hidden targets are left as they are whatever the body says (CDV-88). Trashed targets get the same rule as archived ones: the relationship is Kith data that returns with a restore, and the purge cascade removes it — RFC 6350 §6.6.6 does not require a RELATED URI to resolve, and RFC 6352 lets the server keep data it stores; the client cannot see the target, so it cannot meaningfully manage the link — cost if wrong: a 4.0 client that deliberately removes such a RELATED line does not remove the relationship (the UI still can).
